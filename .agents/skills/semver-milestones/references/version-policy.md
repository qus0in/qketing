# 버전 정책과 로드맵

## 계획·빌드·릴리스 역할

| 역할 | 원본 |
| --- | --- |
| 로드맵·목표·승격 판단 | 호스트가 지정한 로드맵 이슈/문서 |
| 현재 개발 버전 | 빌드 도구의 단일 버전 파일/속성 |
| 산출물 버전 | 빌드 도구가 해석한 실제 버전 |
| 릴리스 커밋 확정 | Git tag `vX.Y.Z` |
| 이미지 추적 | `<image>:X.Y.Z` 및 `<image>:sha-<commit-sha>` |
| 릴리스 기록 | 동일 tag의 GitHub Release |

## 0.x 단계의 운영 정책

- `0.x.0`은 새로운 응집 기능 또는 함께 검증해야 의미가 있는 단위로 사용한다.
- `0.x.y`는 해당 단위의 버그 수정·보완에 사용한다.
  새 기능을 patch에 무조건 넣지 말고 호스트의 호환성·범위 정책으로 판단한다.
- 위 분류는 초기 개발을 위한 운영 정책이다. SemVer 자체가 milestone을 정의하지는 않는다.
- minor는 십진 정수이다. 0.9 다음은 0.10이며 자릿수로 제한하지 않는다.
- 0.x에서는 breaking change를 허용하되 변경과 migration 영향을 기록한다.
  `1.0.0`부터 안정된 공개 계약을 선언한다.
- `1.x` 이후 호환성 파괴는 major, 호환 기능 추가는 minor, 호환 버그 수정은 patch이다.
- minor 증가 시 patch를 0으로, major 증가 시 minor·patch를 0으로 초기화한다.
- 각 숫자에 선행 0을 쓰지 않는다. 문자열 사전순 대신 숫자별로 비교한다.

## 목표와 이슈

- milestone은 layer별 소유권이 아니라 통합 완료 목표를 표현한다.
- 함께 검증해야 하는 기능은 여러 layer·plan을 횡단해 묶는다.
  무관한 기능은 날짜나 버전 번호를 맞추기 위해 합치지 않는다.
- 실제 구현 이슈는 milestone과 로드맵 원본·관련 plan을 참조한다.
  상세 설계는 plan에 두고 로드맵에는 인덱스·진척·승격 판단만 둔다.
- plan이 여러 milestone에 걸치면 단계별 작업 이슈를 분리해 연결한다.
- patch 릴리스는 해당 목표에서 추적하거나 별도 patch milestone을 둔다.
  호스트 정책을 명시하고 완료된 milestone을 말없이 재정의하지 않는다.

## 개발 상태

`<version>-SNAPSHOT → <version> → v<version> → GitHub Release`
흐름으로 승격하고 이후 `<next-version>-SNAPSHOT`을 개발한다.
SNAPSHOT은 개발 산출물 식별자이며 정식 릴리스 이미지 태그로 쓰지 않는다.
0.x 정식 버전도 공개 API 안정성을 보장하는 1.0과는 구분한다.

정의와 불변 릴리스 원칙은 [SemVer 명세](https://semver.org/spec/v2.0.0.html)를 따른다.
