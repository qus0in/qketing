# 라우팅: worker 티어 판별과 업무 배정

## 1. 티어 판별

`scripts/discover-workers.sh`의 `model_hint`를 보고 판단한다. 명시된 신호가 추정보다 우선한다.

| 신호 | 티어 쪽으로 |
| - | - |
| 플래그십 이름 (Opus, GPT-x 메인 라인, Pro 계열) | 상 |
| `Flash`, `Mini`, `Haiku`, `Lite`, `Nano`, `Free` | 하 (경량) |
| effort `high`/`max`/`xhigh` | 한 단계 위 (단, 경량 모델은 최대 "중"까지) |
| effort `low`/`minimal` | 한 단계 아래 |
| 모델을 알 수 없음 | 하로 가정하고 dry-run으로 확인 |

- 판단이 애매하면 작은 작업을 하나 맡겨 보고, 결과 품질로 티어를 보정한다.
- 판별 결과와 근거는 레포 문서(예: `docs/orchestration.md`)에 날짜와 함께 기록한다.

## 2. 업무 유형 → 티어

| 업무 | 최소 티어 | 비고 |
| - | - | - |
| 요구사항 분석, 작업 분해, 최종 리뷰, 머지 판단 | Orchestrator | 위임하지 않는다 |
| 설계가 걸린 구현, 여러 파일에 걸친 리팩터링, 디버깅 | 상 | |
| 코드 리뷰, 보안·버그 탐색 | 상 | 구현한 worker와 다른 worker에게 맡긴다 |
| 명세가 분명한 단일 모듈 구현, 테스트 작성 | 중 | |
| 문서 간 모순 탐지, 로그·출력 분석, 조사 요약 | 중 | |
| 포맷·오탈자, 단순 반복 수정, 파일 목록·사실 조회 | 하 | |
| 테스트·빌드 실행과 결과 요약 | 하 | 또는 Orchestrator가 pane으로 직접 실행 |

- 상위 티어를 하위 업무에 쓰는 것은 괜찮지만, 상위가 바쁘면 하위에 먼저 준다.
- 하위 티어 결과는 반드시 Orchestrator가 검증한다. 상위 티어 결과도 diff는 직접 확인한다.

## 3. 동시 실행 규칙

- 모든 worker가 같은 작업 트리를 공유한다. **쓰기 작업끼리는 파일 소유권이 겹치지 않게** 나눈다.
- 겹칠 수밖에 없으면 순차로 실행하거나, 사용자 동의를 받아 `herdr worktree`로 작업 트리를 분리한다.
- 읽기 전용 작업은 자유롭게 병렬로 실행한다.
- git commit, push, PR은 Orchestrator만 한다. worker에게는 금지한다.

## 4. 재배정

| 결과 | 조치 |
| - | - |
| `FAILED` 또는 품질 미달 | 한 티어 위로 재배정. 실패 원인을 프롬프트에 포함 |
| `BLOCKED` (승인 대기) | 화면을 읽고 사용자에게 확인을 요청한다. 대신 승인하지 않는다 |
| `BLOCKED` (설정값·외부 처리 필요) | `handle` 이슈를 만들고, 그 일에 의존하지 않는 작업을 계속한다 |
| timeout, stalled | 다시 보내지 않는다. `agent read`로 진행 상황부터 확인 |
| 같은 작업이 두 번 실패 | Orchestrator가 직접 처리하거나 사용자에게 보고 |
